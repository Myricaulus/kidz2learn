# Services and shared audio elements

## Cross-cutting services (Services/, singleton unless noted)

- `ScoreService` — base + decaying bonus score (bonus decays on a `System.Threading.Timer`); also self-adjusts a difficulty/pacing target from elapsed time between answers.
- `HudStateService` — combo count / timer visibility / current task difficulty, exposed via `OnChange` for HUD components to subscribe to. `TaskHost` sets the difficulty for every task it loads (and clears it on dispose); `DifficultyIndicator` in the HUD sidebar shows it under the combo.
- Difficulty rewards: `Model/DifficultyInfo.cs` holds the kid-facing icon/label (🎈 Spielen, 💪 Arbeiten, 💣 Bombe) and the point factor (×1 / ×1.5 / ×2) per `Difficulty`. `TaskSessionController.RecordSuccess` scales every success's points by it, so views pass Normal-level points; only points awarded outside of it (Silbenhammer's per-word `Score.AddPoints`) call `DifficultyInfo.Scale` themselves. `Difficulty` is relative to the candidate pool (easiest `DifficultyLevel` = Normal), not to the learner's mastery - see GitHub issue #1.
- `LoggerService` — broadcasts `RenderFragment` log entries (`OnLogAppended`) for an in-page live log.
- `AudioStatusService` — plays every clip (`PlayWordAsync` on `#audioPlayer`, `PlayAsync` for another element) and tracks whether audio is available. The clips come from the app's server, so without a connection they fail: `k4l_playAudioFile` resolves to false when a clip can't be loaded or played or hasn't started within 8 s (a play blocked for autoplay counts as played). A failed clip, or the browser's `offline` event, makes it send a `HEAD` for the affirmations manifest past the cache (`k4l_probeServer`); while that fails, `Available` is false and it asks again every 10 s and on `online`. `MainLayout` shows a "Kein Ton" chip meanwhile. `TaskHost` listens to `OnChange` and `OnWordFailed`: an open task with `BrauchtTon` (the listening exercises `read_syllables`/`read_precise`) ends without scoring anything more, with a snackbar, and the next pick leaves those tasks out (`TryChooseAnyAsync`'s `playable`); a page whose pool is nothing but listening exercises shows a notice and picks again once audio is back. Elsewhere (W-Fragen, Rätsel, tappable words in `LeseSatz`, affirmations) clips are an extra, played without waiting for them.
- `SidWidgetService` — current player volume, exposed via `OnVolumeChanged` so pages/views can duck/restore music (e.g. `SilbenMultipleChoiceView` lowers volume while an exercise is active).
- `SidPlayerService` (scoped) — thin JS-interop wrapper around `wwwroot/js/jsSID.js`'s `window.sidPlayer` (a C64 SID chiptune player) for the `SidPlayerWidget` component; SID files live in `wwwroot/sids`, cataloged in `sidfiles.<hash>.json`. SID tunes loop forever, so the widget switches to a random other tune once the current one has played its HVSC length (`k4l_sidOnEnd`, 3 min if unknown); a new `.sid` needs its two lines from HVSC's `Songlengths.md5` in `tools/data/sid-songlengths.md5`.
- `AffirmationService` (scoped — depends on the scoped `HttpClient`) — plays a random success/failure sound after a task is answered, called from `TaskSessionController` (covering every `TaskHost`-based view) and directly from `TurboArithChallenge`, which isn't on `TaskHost`. Files live in `wwwroot/audio/affirmations/{erfolg,misserfolg}/`, cataloged in `affirmations.<hash>.json` (regenerated before every build by `tools/generate_manifests.py`, see Commands). Both folders are currently empty, so playback silently no-ops until sound files are actually recorded and dropped in.

- `TelemetryService` (scoped) — opt-in per-device session log (every `RecordSuccess`/`RecordFailure` via `TaskSessionController`, with a human-readable `detail`, the time since `TaskHost` showed the task, the definition's `level`, the pool-relative `difficulty`, the `attempt` number within the task, and each skill's mastery before/after scoring - the raw material for tuning the mastery formula). Only devices opened once with `?telemetrie=<url>` (`=off` undoes it) send anything; everywhere else it only logs each attempt to the browser console (as on every device; `copy(k4l_telemetrySession)` there copies the session as JSON) - a fallback for field tests without opt-in, and the endpoint lives only in that device's localStorage, never in the repo. Local dev runs (`dotnet run`/Rider, environment `Development`) always send: `MainLayout` falls back to the `Telemetrie` key of `wwwroot/appsettings.Development.json`, which is gitignored and exists only on the parent's PC. Every session carries `App` (the app's base URL), so `localhost` test sessions stand apart from the kids' ones. It also carries `Koop`: the splash screen's two-person button (next to the one-person button for playing alone) sets `PlayMode.Koop` for the rest of the app run, for when two kids of about the same age play together - answers train only the Koop mastery profile (`SkillStatesKoop`; solo answers train both, a skill Koop hasn't seen starts as a copy of solo, and the picker reads the current mode's profile), Silbenhammer ratings and the views' per-task histories aren't stored, `Beobachtungen` go only into telemetry (flagged `Koop`), not into the reading profile, tasks marked `FuerLeseprofil` (the p/q search grid) are left out of 80 % of the picks, the console log prefixes entries with `[KOOP]`, and `ScoreService` adds only half of every task's points to the YouTube bar and the game time, so two players together need twice the points. On opted-in devices, a failed upload makes the YouTube button ask "Wirklich zu YouTube wechseln?" so the console can be inspected first. The receiving side is `tools/telemetry_receiver.py` (stdlib Python, HTTPS, one JSON file per session), run as a systemd service on the parent's home server. Sessions are fetched without SSH by `tools/telemetry_fetch.py` (token-authenticated `GET`/`DELETE /sessions` on the same receiver; the server holds only the token's SHA-256, the token and URL live in `~/.config/kidz2learn/telemetrie-abruf.json`) into `inbox/telemetrie/`, deleting each session on the server once it's stored locally and untouched for an hour.
- `SpielzeitService` (scoped) — game time for the laptop's games, on devices opened once with `?spiele=steam,heroic,prism` (`=off` undoes it; kept in localStorage). There the beaver's bar is the game-time bar and YouTube is hidden (`Model/Spielzeit.cs`, pure and tested): every point `ScoreService` hands out (`OnPunkte`, after the Koop factor) fills it, the n-th fill of a day needs 30 + 5·(n-1) points and credits 10 minutes, but only once a 💣 was solved during that fill (`TaskSessionController.RecordSuccess` reports it after the points); after a payout the bar is always empty, nothing carries over. A full bar without one stays full, loses further points and makes `TaskHost` force a 💣 (`TryChooseAnyAsync(bombe: true)`: the hardest unlocked candidates, shown as 💣 even when nothing is that hard yet), every other task. Day count and unpaid minutes live in localStorage; every app start begins with an empty bar. One button ("Starten", or "Weiter spielen" while the games are frozen) hands all minutes to the game-time guard on the laptop, `http://127.0.0.1:8768/zeit?min=<n>` (`k4l-waechter`, a user service outside this repo, see the parent's mybilux scripts), which counts time only while a game in Steam/Heroic/Prism really runs (CPU load of the launcher unit's other processes), and freezes and ends the games; they start as usual. A panel widget shows the time left and opens Kidz4Learn ("Aufladen"). The minutes stay in the app when the guard doesn't answer. The app sends it a heartbeat (`/da`, every 10 s), so it knows whether Kidz4Learn is open, and the answer says whether the games are frozen. Cheating is meant to be possible (editable minutes field, `k4l.zeit(n)` announced in the console, the address typed by hand, localStorage) and to show up as a mismatch: telemetry gets a `Spielzeit` list (`Gutschrift`, `Bombe`, `Auszahlung` with the minutes it carried), the handler logs what it received, and the games count their own playtime.

## Shared audio elements (MainLayout.razor)

`#audioPlayer` (word/syllable playback) and `#affirmationPlayer` (success/failure sounds) are both mounted once in `MainLayout.razor`, outside the splash/main-layout `@if` branches, so they're stable DOM nodes across the whole app lifetime — not owned by individual challenge pages. `StartApp()`'s "Starte App" click primes both synchronously (`k4l_primeAudioPlayer` in `wwwroot/js/interop.js`) so the browser ties audio-autoplay permission to that gesture; `AudioStatusService` (calling `k4l_playAudioFile(id, src)`) is what pages use afterward to actually play a file. Keeping the two elements separate matters because a single `<audio>` element can only play one source at a time — sharing one between word narration and affirmations would let either abort the other.
